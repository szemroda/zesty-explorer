Research brief · stan na 2026-09-11

EffectJS w Zesty Explorer

Decyzja dla browser-only Vite + React z nested table: tak, ale Effect powinien objąć I/O i lifecycle, nie całą aplikację. Czyste łączenie, filtrowanie, sortowanie i przygotowanie wierszy pozostają zwykłymi, szybkimi funkcjami TypeScript.

Zakres obejmuje aktualny oficjalny ekosystem Effect, Schema kontra Zod, HTTP w przeglądarce, anulowanie, współbieżność, retry, integrację z React/TanStack Query, language service, Vite, Vitest oraz plan lokalnych testów performance. Badanie nie wykonuje requestów do Zesty, nie używa app.sid i nie zawiera sekretów.

Wniosek wykonawczy

Rekomenduję zacząć od stabilnej linii Effect v3. Oficjalne repozytorium opisuje Effect v4 jako release candidate; v4 przenosi wiele modułów do effect/unstable/*, a te moduły mogą zmieniać się także w ramach minor release. Dla prostego narzędzia, które ma być użyteczne i względnie proste, koszt tej niestabilności nie daje obecnie wystarczającej korzyści.

W v3 używamy effect oraz @effect/platform z fetchowym FetchHttpClient.layer. @effect/platform-browser dokładamy tylko wtedy, gdy faktycznie potrzebne są browser-specific services albo klient XHR. Jeśli projekt świadomie wybierze v4, wszystkie pakiety Effect muszą pochodzić z kompatybilnego tagu @rc; nie wolno mieszać v3 i v4.

Effect daje największą wartość w trzech miejscach: typed failures na granicy API, kontrolowana współbieżność ładowania kolekcji oraz przerwanie/retry/timeout. TanStack Query pozostaje właścicielem cache i stanu zapytań, a React właścicielem renderowania. Nie dokładamy równolegle @effect/atom-react do tego samego rodzaju stanu.

Minimalne moduły i interfejsy

Granice poniżej są celowo małe. Moduł domain/core nie importuje Effect, React, TanStack ani browser API; dzięki temu ma niski koszt wywołania i może zostać użyty w Workerze bez zmian.

1. Czysty model i algorytmy

export type ItemId = string
export type Scalar = string | number | boolean

export interface ContentItem {
  readonly id: ItemId
  readonly fields: Readonly<Record<string, unknown>>
}

export interface CollectionSnapshot {
  readonly collectionId: string
  readonly items: readonly ContentItem[]
}

  readonly byKey: ReadonlyMap<Scalar, readonly ContentItem[]>
}

export interface ExplorerIndexes {
  readonly byCollection: ReadonlyMap<string, JoinIndex>
}

export function relatedItems(
  index: JoinIndex,
  key: Scalar,
): readonly ContentItem[]
export function applyViewFilter(

Implementacja powinna budować każdy indeks raz na identity snapshotu, używać Map zamiast zagnieżdżonych find i zachowywać referencje do itemów. Join oparty o relację custom powinien stosować ścisłą równość scalarów zgodnie z modelem domeny. Filter/sort działa na referencjach lub ID, a nie tworzy głębokich kopii całego datasetu.

2. Effectowa granica I/O

export interface PageRequest {
  readonly url: string
  readonly page: number
  readonly signal: AbortSignal
}

export interface ZestyApi {
  readonly fetchPage: (
    request: PageRequest,
  ) => Effect.Effect<CollectionPage, ZestyError>
}

export interface LoadRequest {
  readonly rootUrl: string
  readonly collectionIds: readonly string[]
  readonly signal: AbortSignal
}

export function loadSnapshot(
  request: LoadRequest,
): Effect.Effect<CollectionSnapshot[], LoadError, ZestyApi>

W realnym kodzie ZestyApi jest serwisem/tagiem dostarczanym przez Layer. Implementacja adaptera pobiera strony, odrzuca niepoprawny status, dekoduje stronę Schema i mapuje błąd transportu/dekodowania na typ aplikacyjny. UI zna tylko loadSnapshot, a nie szczegóły klienta HTTP.

3. Jedyny punkt wejścia z React/TanStack Query

const snapshotQuery = useQuery({
  queryKey: ["snapshot", input.rootUrl, input.collectionIds],
  queryFn: ({ signal }) =>
    Effect.runPromise(
      loadSnapshot({ ...input, signal }).pipe(
        Effect.provide(AppLive),
      ),
    ),
})

To jest schemat granicy, nie gotowy kod zależny od konkretnej wersji API. queryKey musi obejmować wszystkie zmienne używane przez funkcję zapytania. Sygnał TanStack przekazujemy do wszystkich requestów strony. Nie wywołujemy Effect.runPromise w środku innego Effect ani w fazie renderu React.

LiniaOficjalna ścieżkaPraktyczne użycie

Adapter powinien mieć jedno miejsce konfiguracji: base URL, nagłówek autoryzacji, obsługę statusu i dekoder strony. Dla requestów read-only retry jest rozsądny tylko dla błędów przejściowych (np. sieć, 429, 5xx po świadomej polityce), nigdy dla błędu Schema, 4xx wynikającego z danych wejściowych ani przerwania użytkownika. CORS, cookies, redirecty i rzeczywiste zachowanie fetch nadal należą do runtime’u przeglądarki.

Źródła: v3 HttpClient, v3 FetchHttpClient, v3 BrowserHttpClient oraz v4 BrowserHttpClient.

Anulowanie, współbieżność i retry

Anulowanie

TanStack Query przekazuje AbortSignal do queryFn. Domyślnie nie anuluje obietnicy, gdy komponent znika; gdy funkcja skonsumuje sygnał, anulowanie fetch powoduje również cofnięcie stanu query. To dokładnie ten sygnał, który powinien trafić do Effectowego adaptera.

Effect może przerwać fiber i posprzątać zasoby. W praktyce: zmiana query key, unmount albo ręczne cancelQueries kończy requesty stron, zamiast pozwalać im wyścignąć nowy snapshot.

Współbieżność

Effect domyślnie wykonuje efekty sekwencyjnie; Effect.all lub Effect.forEach może przyjąć limit. Dla ładowania pozostałych kolekcji zacząć od concurrency: 3. To amortyzuje latency bez otwierania nieograniczonej liczby requestów.

Nie uruchamiać jednego Effectu na każdą komórkę lub item. Współbieżność dotyczy requestów kolekcji/stron, nie czystych joinów.

Timeout

Timeout powinien kończyć program przerwaniem źródła, a nie zostawiać fetch w tle. Ustalić jedną wartość na request lub całą operację ładowania i pokazać użytkownikowi rozróżnienie timeoutu od błędu danych.

Retry

Effect ma Effect.retry i Schedule. Użyć krótkiego limitu i backoffu tylko dla typed transient errors. W TanStack Query nie dublować automatycznie tej samej polityki — wybrać jedno miejsce odpowiedzialne za retry, najlepiej adapter Effect.

const loadRelated = Effect.forEach(
  collectionIds,
  (collectionId) => loadCollection(collectionId).pipe(
    Effect.retry(transientSchedule),
    Effect.timeout("15 seconds"),
  ),
  { concurrency: 3 },
)

Przykład pokazuje intencję i kolejność kontroli; konkretne nazwy helperów mogą różnić się między v3 i v4. Nie retry’ujemy interruption/cancel, błędów walidacji ani zwykłych błędów 4xx. Źródła: Effect concurrency, Effect retry, Effect timeout oraz TanStack Query cancellation.

React i TanStack Query bez nakładania abstrakcji

Najprostszy podział to: TanStack Query = server state i cache, Effect = wykonanie jednego programu, React = stan interakcji i render. Query function zwraca Promise, więc na tej jednej krawędzi wykonujemy przygotowany program przez Effect.runPromise. Wewnątrz programu używamy usług/layers, nie globali.

WzorzecZastosowanie tutaj
Query keyUwzględnia identyfikator instancji, root collection, wybrane kolekcje, view/filter inputs i wersję snapshotu, jeśli wpływają na wynik.
queryFn({ signal })Przekazuje sygnał do wszystkich requestów Effectowego loadera; nie ignoruje cancellation.
selectMoże wyciągać lekkie pochodne dane. Duży nested tree lepiej wyprowadzać memoizowaną czystą funkcją zależną od identity snapshotu i stanu UI.
Dependent/prefetch queriesUżywać dla rozwijanej kolekcji, jeśli nie chcemy pobierać całego grafu od razu. Klucz query powinien opisywać konkretną kolekcję.
@effect/atom-reactNie dodawać w MVP. To v4-owe bindingi do Atom, a wprowadzenie drugiego mechanizmu cache/reactivity zwiększa koszt poznawczy i ryzyko duplikacji stanu.

Nie tworzyć trwałego Effect fiber dla każdego renderu. Program uruchamia Query, a lifecycle Query i jego sygnał kończą pracę. Przy manualnym przycisku „Load” można uruchomić program w callbacku i zapisać wynik do QueryClient albo pozostawić całe ładowanie jako query.

Źródła: query keys, useQuery, render optimizations, dependent queries oraz oficjalne @effect/atom-react.

Effect language service: tak, z ograniczeniami

Language service jest dobrą inwestycją w tę bazę kodu: wykrywa m.in. floating Effects, brakujące wymagania/error context, problemy z Layer oraz duplikaty pakietów; oferuje też quickinfo i refactory. Nie jest jednak zamiennikiem tsc, Vitest ani Vite build.

Konfiguracja dla TypeScript poniżej 7

pnpm add -D @effect/language-service typescript@^5.9
{
  "$schema": "./node_modules/@effect/language-service/schema.json",
  "compilerOptions": {
    "strict": true,
    "plugins": [
      { "name": "@effect/language-service" }
    ]
  }
}
  • Plugin powinien być ostatnim wpisem w plugins.
  • VS Code musi używać workspace TypeScript z projektu.
  • Vite tylko transpile’uje TypeScript; uruchamiamy osobne tsc --noEmit.
  • CLI pnpm exec effect-language-service diagnostics --project tsconfig.json daje lokalny raport bez patchowania TypeScript.
Nie patchować tsc na starcie. Oficjalny plugin ma effect-language-service patch, który modyfikuje lokalne pliki TypeScript w node_modules i może wymagać pełnego rebuilda/wyczyszczenia tsbuildinfo. Dla projektu bez CI wystarczy plugin w edytorze, tsc --noEmit i opcjonalny CLI diagnostics. Patch można włączyć świadomie dopiero, gdy brak build-time diagnostics będzie realnym problemem.

Jeśli projekt przejdzie na TypeScript 7, aktualny README language service zaleca zamiast pluginu użyć @effect/tsgo. To osobna decyzja narzędziowa; nie instalować obu bez potrzeby.

Źródło: oficjalny README @effect/language-service.

Vite, tree-shaking i koszt bundle

Effect nie powinien być oceniany po liczbie plików w dev serverze. Vite pre-bundle’uje zależności w development, a produkcyjny build przechodzi przez tree-shaking. Mimo to importy i moduły mają znaczenie:

  • Preferować importy z konkretnych modułów, np. effect/Effect, effect/Schema, effect/Schedule oraz @effect/platform/HttpClient, zamiast budowania własnych barrel files.
  • Efektowe funkcje są tree-shakeable; bundler musi jednak poprawnie analizować zakresy. Rollup/Rolldown i Webpack 5+ są wskazane w dokumentacji Effect jako wspierające deep scope analysis.
  • @effect/language-service, vitest i @effect/vitest są devDependencies i nie trafiają do runtime bundle.
  • Nie importować @effect/atom-react ani modułów Stream/Worker, jeśli nie są używane.
  • Po pierwszej implementacji uruchomić realny pnpm vite build i zapisać rozmiar initial chunk. Nie optymalizować na podstawie intuicji.

Vite zaleca unikanie barrel files oraz dynamiczne importowanie dużych zależności używanych warunkowo. Dependency pre-bundling poprawia development, ale działa tylko w dev, więc decyzję o bundle podejmujemy na produkcyjnym buildzie.

Źródła: Effect imports/tree-shaking, Vite dependency pre-bundling, Vite performance i Vite features.

Plan performance dla nested table

Nested table ma dwa różne koszty: obliczenie grafu i render DOM. Effect pomaga tylko w pierwszym przypadku, jeśli graf wymaga asynchronicznych requestów. Sam join nie staje się szybszy przez opakowanie go w Effect.

EtapImplementacja startowaCel pomiaru
PobranieJedno query dla snapshotu albo query per kolekcja; limit Effect concurrency 3; pages bounded.Brak lawiny requestów i możliwość przerwania starego query.
NormalizacjaSchema decode raz na stronę; itemy są immutable/referencyjne od tego momentu.Brak ponownego parse całego datasetu przy filtrze.
IndeksMap<Scalar, ContentItem[]> na kolekcję; budowa raz dla identity snapshotu.Zamiast O(root × related) uzyskać lookup O(1) średnio po przygotowaniu O(n).
Widoczne rowsMemoizowane flatten tylko dla rozwiniętych gałęzi; filtr i sort na ID/ref.Praca proporcjonalna do widocznego wyniku, nie do liczby komórek.
DOMStabilne klucze, małe komponenty, render tylko flattened visible rows; windowing, gdy liczba wierszy tego wymaga.Brak setek/tysięcy niepotrzebnych nodes i rerenderów.

Na start użyć useMemo dla funkcji zależnej od identity snapshotu, filtrów i expansion state. Dla wyszukiwania można dodać krótkie opóźnienie albo useDeferredValue, ale dopiero po pomiarze. Jeśli widocznych jest dużo wierszy, windowing jest ważniejszy niż przenoszenie joinu do Workera.

Próg dla Web Workera: najpierw naprawić algorytm, memoizację i liczbę renderowanych wierszy. Worker ma sens dopiero, gdy syntetyczne dane realistycznego rozmiaru nadal tworzą długie taski (około 50 ms lub więcej) podczas filtrowania/flattening albo p95 interakcji przekracza uzgodniony budżet.

Opcjonalna ścieżka Web Worker

Pure core może zostać przeniesiony bez zmiany interfejsu. Worker nie powinien znać TanStack Query, tokenu ani Effectowego klienta HTTP; dostaje serializowalny snapshot i polecenie wyliczenia rows.

type CoreRequest = {
  readonly requestId: number
  readonly op: "deriveRows"
  readonly snapshot: SerializableSnapshot
  readonly filter: FilterInput
  readonly expanded: readonly string[]
}

type CoreResponse =
  | { readonly requestId: number; readonly ok: true; readonly rows: readonly Row[] }
  | { readonly requestId: number; readonly ok: false; readonly message: string }

Na głównej stronie utrzymujemy tylko jeden worker, numerujemy requesty i ignorujemy odpowiedzi starsze niż aktualny input. Trzeba mierzyć także koszt structured clone; przeniesienie dużego snapshotu może zjeść zysk. Vite rekomenduje standardowy konstruktor:

const worker = new Worker(
  new URL("./explorer.worker.ts", import.meta.url),
  { type: "module" },
)

W produkcyjnym buildzie Vite emituje Worker jako osobny chunk. To pozwala nie obciążać initial bundle, ale jest kolejnym lifecycle’em do testowania i zamknięcia. Nie dodawać go do pierwszej wersji bez czerwonego wyniku benchmarku.

Źródło: Vite Web Workers.

To daje powtarzalną decyzję bez udawania, że każdy komputer ma ten sam czas.

Kryteria akceptacji implementacji

  1. Ścieżka happy path ładuje fixture przez fake transport, bez sieci, app.sid i prawdziwej instancji Zesty.
  2. Zmiana query key lub unmount konsumuje AbortSignal i nie pozwala staremu snapshotowi nadpisać nowego.
  3. Ładowanie wielu kolekcji ma jawny limit concurrency (start: 3), bounded pages i test pokazujący, że limit działa.
  4. Join/filter/sort/flatten są pure, mają indeks O(n), nie mutują danych i nie są uruchamiane jako Effect.
  5. Nested table renderuje tylko widoczne, spłaszczone rows i nie dekoduje/łączy danych na poziomie komórki.
  6. Local performance command działa z syntetycznymi fixture’ami i pokazuje baseline/regresję dla 10k i 50k.
  7. pnpm vite build potwierdza, że initial bundle jest akceptowalny; Worker pozostaje opcjonalny i osobno chunkowany.
  8. Language service jest używalny w workspace TS, ale nie wymaga patchowania tsc ani dodatkowego CI.

Koszty i świadome „nie”

Co zyskujemy

  • Typed failure zamiast rozlanego catch (unknown).
  • Jedną politykę timeout/retry/concurrency i poprawne cleanup po interrupt.
  • Testowalne usługi: real Layer i fake Layer mają ten sam interfejs.
  • Łatwą zmianę transportu bez dotykania pure core i tabeli.

Czego nie używamy w MVP

  • Effect Atom/React jako drugi server-state store.
  • Stream, jeśli nie potrzebujemy progresywnego renderowania stron.
  • RPC/HTTP API codegen, bo aplikacja nie tworzy własnego serwera.
  • Web Worker, dopóki benchmark nie pokaże długich tasków.
  • Effect w czystych pętlach tylko po to, by „wszystko było Effect”.

Najważniejsza zasada: Effect ma być głębokim modułem wąskiej granicy I/O, a nie płytką warstwą opakowującą każdą funkcję. Dzięki temu zachowujemy typed lifecycle bez płacenia złożonością w najgorętszej ścieżce nested table.
