Research brief · 2026-09-11

Zesty.io API dla aplikacji działającej bez backendu

Zakres: bezpośrednie requesty z przeglądarki do Zesty, token wprowadzany lokalnie (nigdy w URL), kolekcje/content models, latest saved vs published, relacje i zagnieżdżenia, paginacja, filtracja oraz limity. „Manager API” jest poniżej nazywane oficjalną nazwą Instances API.

Wszystkie ustalenia opierają się na dokumentacji Zesty.io oraz oficjalnych repozytoriach organizacji Zesty.io. Artefakt nie zawiera tokenów ani innych sekretów.

Wniosek wykonawczy

Dla założenia „Vercel SPA → bezpośrednio Zesty” podstawą powinien być Instant API, nie Instances API. Instant API jest read-only, ma opisane ustawienia CORS i URL-e oparte o domenę preview/live. Instances API daje lepszą kontrolę nad wersjami, schematem i paginacją, ale dokumentacja nie opisuje ustawienia CORS dla zewnętrznego originu; oficjalny kod Manager UI pokazuje, że lokalna kopia UI musi omijać problem CORS przez host routing. Nie należy więc zakładać, że requesty z domeny Vercel zadziałają.

Jeśli organizacja nie może włączyć CORS dla Instant API albo kolekcje są dostępne wyłącznie przez REST API, wymaganie „bez żadnego endpointu po naszej stronie” staje się blockerem — trzeba wtedy uzyskać potwierdzenie od Zesty dla konkretnej instancji albo zaakceptować proxy/backend.

1. CORS i wybór API

APICo dokumentują źródłaKonsekwencja dla SPA
Instances API
RESTread/write		 Oficjalny endpoint ma postać https://{instance_zuid}.api.zesty.io/v1/ i wymaga nagłówka autoryzacji. Zesty nie wskazuje w ustawieniach instancji analogicznego przełącznika „allow external origin” dla tego API. Dokumentacja trybów mówi, że WebEngine modes nie wpływają na Read/Write APIs (w tym Instances API). Oficjalny README Manager UI opisuje, że lokalne requesty do zdalnych zasobów wpadają w CORS i wymagają host routing. Ryzyko wysokie / brak gwarancji browser CORS. Można testować na konkretnej instancji, lecz architektura nie może opierać się na tym bez potwierdzenia. REST jest dobry dla narzędzia serwerowego lub działającego w originie Managera.
Instant API
GETread-only		 Jest opcjonalnie włączany w Developer settings. Zesty opisuje CORS dla Instant API: w ustawieniach można dopuścić zewnętrzne domeny; w Traditional mode remote origins są odrzucane, chyba że zostaną jawnie dozwolone, a Headless/Hybrid mode ustawia CORS na *. Źródła: CORS guide, Modes, Instant API. Najlepszy kandydat dla browser-only. Użytkownik musi włączyć Instant JSON API oraz odpowiednią regułę CORS (preferowany konkretny origin Vercel zamiast szerokiego wildcardu, jeśli ustawienia na to pozwalają).
toJSON / custom endpoint
WebEngine		 toJSON potrafi zwracać zhydradowane dane relacyjne, a custom JSON endpoint może kształtować i łączyć dane. Są to jednak endpointy WebEngine na instancji Zesty, a nie endpointy aplikacji. Możliwa alternatywa, ale wymaga konfiguracji/kodu w Zesty i nie daje automatycznie kolekcji z paginacją. Nie przyjmować jako podstawy MVP bez zgody na utrzymywanie endpointów w Zesty.
Preflight: nagłówek Authorization oznacza request, którego browser może sprawdzić przez OPTIONS. Zesty wyjaśnia, że dodatkowe nagłówki muszą być dopuszczone w Access-Control-Allow-Headers; jeśli origin lub nagłówek nie przejdzie preflightu, kod JavaScript nie ma sposobu, aby CORS obejść. Przed implementacją trzeba wykonać realny test OPTIONS/GET na jednej instancji.

2. Token i autoryzacja

ŚcieżkaAuthWażne ograniczenia
Instances API Authorization: Bearer <access-token>. OpenAPI każdego endpointu deklaruje security scheme typu Bearer. Access token jest opaque, ważny 90 dni, przypisany do roli i instancji. Tworzyć go może tylko Admin/Owner; warto użyć custom role z wyłącznie uprawnieniami odczytu. Wartość jest widoczna tylko podczas tworzenia i jest sekretem. Źródło: Auth API.
Instant API Opcjonalny prywatny token ustawiany w Developer settings, także przesyłany jako Authorization: Bearer XXXXX. Dokumentacja nazywa go „private token” i nie gwarantuje, że jest tym samym tokenem co access token Instances API. UX powinien rozróżnić tryb/token albo jasno założyć tylko jeden wspierany wariant.
  • Token nie może być zapisywany w query params, historii URL, logach ani treści linku share.
  • Najbezpieczniejszy domyślny stan dla aplikacji to pamięć sesji (wpisanie po otwarciu); jeśli produkt zapisuje go lokalnie, należy uznać to za świadomy kompromis bezpieczeństwa.
  • URL sharing powinien zawierać wyłącznie konfigurację kolekcji, relacji i filtrów. Osoba otwierająca link wpisuje własny token.
  • Preview URL może być objęty Preview Lock / Headless Authorization. Błąd 401/403 nie zawsze oznacza zły model URL; trzeba sprawdzić security settings instancji. Źródło: Security.

3. Latest saved vs published

Potrzeba w aplikacjiInstances APIInstant/WebEngine
Latest saved (domyślnie) GET /v1/content/models/{model_zuid}/items bez _active. Dokumentacja mówi o najnowszej wersji / ostatniej edycji. Użyj domeny dev/preview. Zesty definiuje dev jako najnowszą wersję contentu, niezależnie od tego, czy została opublikowana.
Published only Dodaj _active=true; dokumentacja definiuje to jako currently active version. To właściwa ścieżka dla checkboxa „published”, ale etykieta w UI powinna brzmieć „active/published” do czasu potwierdzenia na danych instancji. Użyj domeny live/production. Zesty definiuje live jako wyłącznie opublikowany content. Nie używaj preview URL do widoku publikowanego.
Kontrola historii publikacji GET /v1/content/models/{model_zuid}/items/{item_zuid}/versions?published=true filtruje wersje pojedynczego itemu; GET /v1/content/models/{model_zuid}/publishings?showActiveOnly=true zwraca aktywne lub zaplanowane rekordy publikacji. To metadane publikacji, nie zamiennik kolekcji contentu. Do tabeli nadal trzeba pobrać właściwe itemy. 
// REST — domyślny latest saved
https://INSTANCE_ZUID.api.zesty.io/v1/content/models/MODEL_ZUID/items?limit=2500&page=1

// REST — currently active / published view
https://INSTANCE_ZUID.api.zesty.io/v1/content/models/MODEL_ZUID/items?_active=true&limit=2500&page=1

Źródła: Get All Items, Get Item, Get All Item Versions, Get All Model Items Publishings, Environment States, Zesty URLs.

4. Content model / kolekcja i formy URL

W terminologii Zesty „kolekcja” odpowiada najczęściej content model. Model jest schematem i zbiorem itemów; każdy item jest dostępny względem modelu w Instances API.

TypZUIDZnaczenie dla parsera
Instance8-...Host REST API: INSTANCE_ZUID.api.zesty.io.
Content model6-...Kolekcja/model; odczyt schematu: /v1/content/models/{model}; pola: /fields.
Content item7-...Wiersz kolekcji; REST wymaga jednocześnie model ZUID i item ZUID.
Item version9-... / numer wersjiHistoria zapisu; nie jest kolekcją.
Content field12-...Metadane pola, w tym typ i relatedModelZUID.
Publishing record18-...Rekord publikacji; przydatny do statusu, nie do zastąpienia danych itemu.

Źródła identyfikatorów: ZUID Specification oraz Node Instance Content.

Minimalne formy inputu kolekcji

// Instant API — model/collection (preview albo live domain)
https://SITE_OR_PREVIEW_DOMAIN/-/instant/6-MODEL_ZUID.json

// Instant API — pojedynczy item
https://SITE_OR_PREVIEW_DOMAIN/-/instant/7-ITEM_ZUID.json

// Instances API — collection endpoint
https://INSTANCE_ZUID.api.zesty.io/v1/content/models/6-MODEL_ZUID/items

Instant API oficjalnie opisuje format ogólny /-/instant/{zuid}.json, osobno modele (6-) i itemy (7-). Input parser może przyjąć te dwa URL-e oraz REST collection URL, usunąć istniejące query params i zachować jedynie dozwolone parametry aplikacji. Nie należy wymagać od użytkownika ręcznego wpisywania instance ZUID, jeśli można go wyciągnąć z hosta.

5. Relacje i zagnieżdżone dane

  • Zesty wspiera relacje one-to-one i one-to-many. Definicja pola zawiera m.in. typ relacji oraz relatedModelZUID/relatedFieldZUID. Źródła: Content Relationships i Fields.
  • Instant API zwraca relację jako obiekt z totalItems oraz tablicą referencji itemów, np. { type: "item", zuid: "7-...", resourceURI: "/-/instant/7-....json" }. Referencja jest ścieżką do kolejnego requestu, a nie gotowym, zagnieżdżonym itemem.
  • Względna wartość resourceURI musi być rozwiązywana względem domeny źródłowej Zesty (preview/live), nie względem originu Vercel.
  • toJSON dla pojedynczego itemu potrafi zwrócić zhydradowane obiekty relacji; domyślna głębokość hydracji to trzy poziomy. To nie jest jednak udokumentowany zamiennik listowania całego modelu. Źródło: Headless & Hybrid toJSON.
Konsekwencja dla modelu domenowego: połączenie powinno mieć co najmniej parent collection → relation field → child collection, opcjonalną głębokość oraz strategię rozwiązywania referencji. Aplikacja powinna deduplikować requesty po source domain + item ZUID + state + lang, wykrywać cykle i ładować relacje leniwie albo z ograniczoną głębokością. Eager fetch wszystkich relacji może łatwo zamienić 2 000 wierszy w tysiące requestów.

„Filtr po nested data” jest więc filtrem po lokalnie znormalizowanym grafie danych. Przed pobraniem relacji filtr może działać tylko po referencji/ZUID; po pobraniu — po ścieżce typu nested_obj.x. Instant API nie dokumentuje jednego endpointu, który wykonałby taki arbitralny filtr cross-collection za aplikację.

6. Paginacja i limity

ŹródłoUdokumentowane parametryImplikacja
Instances API: items page zaczyna się od 1; page=0 jest błędem. limit ma maksimum 5 000, domyślnie 2 500. Można sortować przez order=created|modified i dir=ASC|DESC. Odpowiedź ma _meta.totalResults, start, offset, limit. Dla aplikacyjnego limitu 10 000 trzeba obsłużyć co najmniej dwie strony po 5 000; praktyczniej pobierać np. 500–2 000 i renderować tabelę wirtualizowaną. Źródło: Get All Items.
Instances API: models GET /content/models zwraca tablicę modeli; endpoint nie deklaruje parametrów paginacji. Lista modeli jest mała względem itemów; cache’ować per instance i token/session.
Instances API: search /v1/search/items: q, limit 1–1 000 (domyślnie 100), page, sortowanie i daty. Search obejmuje ZUID-y oraz meta/path (URL path, full path, navigation text, meta title/description/keywords). Może przyspieszyć wyszukiwanie meta/path, ale nie zastępuje free-textu po dowolnych polach i nested data. Źródło: Search Content Items.
Instant API: model Dokumentacja opisuje URL modelu, ale nie deklaruje parametrów page/limit ani maksymalnej liczby elementów. Nieznany limit. Dla 600–2 000 należy zmierzyć payload na realnej kolekcji; dla 10 000 nie zakładać bezpieczeństwa bez testu. W UI ustanowić twardy guard rozmiaru odpowiedzi/rekordów i komunikat o ograniczeniu.

GraphQL ma osobno udokumentowane limit maksymalnie 100 i page od 1, ale wymaga włączenia GQL i nie rozwiązuje problemu tokenu/CORS dla Instances API. Nie jest potrzebny do MVP opartego o Instant API. Źródło: GraphQL.

7. Rate limiting

Instant/WebEngine: oficjalny guide podaje limit orientacyjny około 10 RPS. Przekroczenie 600 requestów w 60 sekund rozpoczyna blokadę; kolejne requesty dostają 429, a ban trwa 30 minut. Zasada dotyczy WebEngine service requests, wprost wymieniono m.in. Instant API, custom API i toJSON. Media traffic ma inną architekturę.

Dokumentacja przejrzana dla Instances API nie podaje liczbowego limitu. To znaczy „brak znalezionej wartości dokumentacyjnej”, nie „brak limitu”. Klient powinien mieć ograniczoną współbieżność, cache, exponential backoff dla 429/5xx i anulowanie nieaktualnych requestów.

Źródło: Headless: Rate Limiting.

Dla relacji nested szczególnie ważne jest lazy loading, deduplikacja i limit głębokości. Przy wielu użytkownikach wspólny publiczny Instant API może zostać obciążony z jednego browserowego originu; nie budować automatycznego N+1 bez liczników i ostrzeżeń.

8. Rekomendowany kontrakt MVP

  1. Input: kolekcja jako pełny Instant model URL (.../-/instant/6-....json); opcjonalnie REST collection URL tylko za feature flagą/testem CORS.
  2. State: query param aplikacji state=latest domyślnie wybiera preview/dev; state=published wybiera live albo REST _active=true. Nie wkładać tokenu do URL.
  3. Schema: pobrać model/fields, gdy używany jest REST; dla Instant wyprowadzić kolumny z payloadu i relation descriptors. Pola relacji powinny ujawniać child model oraz status hydracji.
  4. Joins: konfiguracja lokalna przechowuje referencję pola i kolekcję docelową. Wspierać depth cap, cycle detection, request budget i cache.
  5. Filtering: free-text i filtry per kolumna wykonuj lokalnie; nested predicate operuje na znormalizowanym path evaluatorze (`nested_obj.x === 123`) z bezpiecznym traktowaniem brakujących wartości.
  6. Sharing: w query params umieścić URL-e kolekcji, state, lang, relacje, sort, free-text i filtry; serializować deterministycznie. Token zawsze z pamięci formularza użytkownika.
  7. UX błędu: rozróżnić CORS/preflight, 401/403, 404 ZUID, 429 rate limit, payload ponad limit i wygasły token. Dodać akcję „sprawdź endpoint” bez ujawniania tokenu.

9. Rzeczy do potwierdzenia na jednej realnej instancji

  • Czy docelowa instancja ma włączony Instant JSON API i jaki dokładnie origin CORS można ustawić.
  • Czy preview URL ma Preview Lock oraz czy Instant API honoruje skonfigurowany private token w obu stanach dev/live.
  • Czy model Instant zwraca całą kolekcję bez paginacji oraz jaki jest rozmiar payloadu dla 2 000 rekordów.
  • Czy `_active=true` na konkretnej instancji zachowuje się jako oczekiwany published-only view dla itemów usuniętych/unpublished/scheduled; w razie potrzeby porównać z showActiveOnly=true na publishing records.
  • Czy potrzebny jest język inny niż domyślny; REST obsługuje lang=en-US, a parser query powinien go zachować poza tokenem.
