shadcn/ui with Base UI for a local React + TypeScript explorer

A practical recommendation for scaffolding the app with npm, understanding the Base UI runtime, keeping the product dark-only, and implementing root and nested data tables with accessible previews and detail panels.

Scope: official shadcn/ui, Base UI, React, Vite, and TanStack documentation/source only. This is a design and implementation brief; it does not change the application.

Decision in one minute

Build tool

Vite with the official react-ts template. React’s from-scratch guidance recommends Vite when a full framework is not needed, and Vite supports a React TypeScript template.[S1][S2]

Component base

Use shadcn/ui’s Base UI base. As of July 2026, Base UI is the default for new shadcn projects; Radix remains supported, but the two APIs must not be mixed casually.[S3][S4]

Table engine

Use shadcn’s source Table primitives plus @tanstack/react-table. TanStack supplies headless state and logic; the app owns markup, styling, and interaction policy.[S5][S6]

Recommended product shape: one typed table component per collection node (Articles, Authors, Offices), each with its own filter/sort/expansion state keyed by relationship path. Root view filters decide which root rows survive; a nested table filter decides which rows that table renders. This state model is an app-level recommendation, not behavior supplied automatically by shadcn or TanStack.

What “shadcn Base UI” actually means

shadcn/ui is a code-distribution system, not a conventional component package: the CLI adds component source to the project, and the team owns the top layer of that code.[S7]

ConceptMeaningWhat it controlsWhat it does not mean
base: "base" Choose Base UI as the primitive/component behavior source. The current CLI exposes base, radix, and aria choices for initialization.[S8] Component APIs, generated imports, behavior, interaction state, and available props. It is not a color theme and it is not the same thing as Tailwind.
style / base-nova The visual treatment is separate from the primitive base. In the v4 registry, compound names such as base-nova are generated from a Base UI base plus a visual style; verify the normalized result with npx shadcn@latest info --json.[S9][S10] Class names, token values, density, radius, and the overall visual language. It is not a runtime package and does not decide whether a component imports Radix or Base UI by itself.
@base-ui/react Base UI’s React runtime. It is headless and unstyled: it ships behavior and accessibility primitives, not a CSS theme. It supports Tailwind, CSS Modules, plain CSS, CSS-in-JS, and Vite.[S11][S12] ARIA/role behavior, keyboard and pointer interactions, focus management, portals, positioning, and state attributes. It is not shadcn’s visual layer and it does not replace the copied files in src/components/ui.
Generated shadcn files Styled wrappers and composition conventions that import Base UI primitives. The official Base UI button source imports Button from @base-ui/react/button and adds the project’s classes/variants.[S13] Design tokens, variants, spacing, visual states, and the local import surface. They are not an opaque dependency that prevents customization.

Base/Radix API boundary: Base UI uses render for custom composition where Radix uses asChild. For a Base UI trigger, use the Base UI form of the generated component and do not paste a Radix example into it. The official shadcn guidance also calls out Base UI’s nativeButton={false} requirement when rendering a button-like component as a non-button element.[S4]

Recommended npm scaffold

Use the explicit Vite react-ts template first, then initialize shadcn in that existing project. This removes ambiguity about framework and TypeScript mode while keeping the shadcn configuration deterministic.

npm create vite@latest zesty-explorer -- --template react-ts
cd zesty-explorer
npm install

# Tailwind v4 + Vite integration, per the shadcn Vite guide
npm install tailwindcss @tailwindcss/vite
npm install -D @types/node

# Base UI primitives + the selected shadcn visual preset
npx shadcn@latest init --base base --preset base-nova --no-monorepo --yes

# TanStack’s headless React table adapter
npm install @tanstack/react-table

# Add only the source components this UI needs initially
npx shadcn@latest add table popover sheet tooltip

npm run dev

The first command is the official React/Vite recommendation adapted to npm. The shadcn CLI’s documented flags are --template, --base, --preset, --name, and --no-monorepo; init installs dependencies, the cn helper, and CSS-variable configuration.[S1][S14][S8]

Required Vite alias wiring

For an existing Vite project, the official shadcn guide asks for the @/* path in both Vite’s TypeScript config and the app config, plus the matching Vite resolve alias. Keep the generated paths and aliases aligned.

// tsconfig.json and tsconfig.app.json (inside compilerOptions)
"baseUrl": ".",
"paths": { "@/*": ["./src/*"] }

// vite.config.ts
import path from "path"
import tailwindcss from "@tailwindcss/vite"
import react from "@vitejs/plugin-react"
import { defineConfig } from "vite"

export default defineConfig({
  plugins: [react(), tailwindcss()],
  resolve: {
    alias: { "@": path.resolve(__dirname, "./src") },
  },
})

The official Vite guide also uses @import "tailwindcss" as the starting CSS import. Let shadcn’s initialization add its own shadcn/tailwind.css import and token block; do not delete the generated tokens when adding the dark-only policy.[S14][S8]

Direct shadcn scaffold (alternative)

The CLI can also create a new Vite project when --name is supplied. Use this only if accepting the CLI’s template defaults; inspect the result and confirm TypeScript is enabled before proceeding.

npx shadcn@latest init --name zesty-explorer --template vite --base base --preset base-nova --no-monorepo --yes

The explicit Vite react-ts path above remains the preferred recommendation because the React and Vite documentation make the React/TypeScript choice visible in the command itself.[S8][S2]

Version gate

Check Node before scaffolding: the current Vite guide requires Node.js 20.19+ or 22.12+; some templates may require a higher version.[S2]

node --version
npm --version

Dark-only theming

Keep shadcn’s CSS-variable mode enabled. The documented model is semantic tokens such as background, foreground, primary, popover, border, and ring, with dark values under a .dark selector. The recommendation here is to force that selector permanently and remove the mode toggle from the product UI.[S15]

<!-- index.html: set before the Vite bundle runs, avoiding a light flash -->
<html lang="en" class="dark">

/* src/index.css: retain shadcn’s generated imports and tokens */
@import "tailwindcss";
@import "shadcn/tailwind.css";
@custom-variant dark (&:is(.dark *));

/* Keep the generated semantic token values in the .dark block. */
.dark {
  color-scheme: dark;
  /* background, foreground, card, popover, primary, ... */
}

This is an implementation recommendation derived from shadcn’s documented .dark token model and Vite dark-mode example. There is no need for a light/system theme provider or a theme toggle if the product intentionally supports dark only; keeping the class static is also preferable to client-side theme negotiation for this requirement.[S16][S15]

  • Use semantic utilities (bg-background, text-foreground, border-border, ring-ring) rather than hard-coded light/dark color pairs.[S15]
  • Keep visible :focus-visible styling. Base UI manages focus movement but explicitly leaves visible focus indication to the application.[S17]
  • Review contrast for muted text, borders, focus rings, hover previews, and selected rows. Base UI provides behavior; it does not choose your colors.[S17]

Table and nested-table model

shadcn deliberately documents a data-table recipe rather than a universal data-table component because table requirements and data sources differ. The recipe starts with the source <Table /> component and adds TanStack Table for state and logic.[S5]

Articlesroot table; view filters; one row per root item
Authorschild table; local filter/sort; complete relation rows
Officesnext child table; local filter/sort; own expansion state

Dependencies and feature selection

  • npm install @tanstack/react-table is the official React adapter install. The current TanStack docs identify the React adapter as working with React 18 or newer, so the Vite React template satisfies the minimum.[S18]
  • The current shadcn data-table guide uses TanStack Table v9’s feature-based API: opt into sorting, filtering, pagination, visibility, selection, and expansion explicitly. Unregistered features can be tree-shaken; filter and sort functions used by the columns must be registered on the features object.[S5]
  • Do not copy older v8 examples that rely on get*RowModel table options into a v9 feature-based implementation. The current guide says optional row models are created and registered on the feature configuration.[S5]

What to do with nested tables

TanStack supports nested sub-row data and expanded row models, but intentionally does not invent the row-toggle UI. The app must add a button in the row and decide how the expanded content is rendered.[S19]

  1. Use a separate table instance/component for each collection node when each relationship level has its own filters, sort order, columns, or pagination. Key the state by a stable relationship path such as articles.authors and articles.authors.offices.
  2. For simple hierarchical rows, use TanStack’s expanding feature with subRows and getSubRows. Render the child collection in the expanded parent row, preferably in a single cell spanning the parent table’s columns. This placement is an app-level markup recommendation that preserves a clear parent/child boundary; TanStack leaves the markup to the application.[S20]
  3. Add a real, labeled button for expansion. Expose its expanded state and relationship in the accessible name, for example Expand authors for “Article title”, and keep Enter/Space behavior native. Base UI’s accessibility guidance requires application-owned accessible names and visible focus styling for custom controls.[S17]
  4. If the API fetches children on demand, use TanStack’s manual-expanding mode and keep loading/error/empty states inside the expanded cell. The guide documents manualExpanding: true for server-side expansion.[S19]

Expansion stability: TanStack sorts expanded rows with the rest by default. Data or grouping changes may reset expansion; if the explorer should keep open branches while edits or filter changes recompute rows, evaluate autoResetExpanded: false (and, when pagination is present, the corresponding page-index reset policy).[S19]

Filter semantics for this explorer

Implement two explicit scopes in app state:

ScopeEffectNested rendering
View filterFilters root rows using root content fields and related values; a related match keeps its root article.Keep the relation complete after the root row survives.
Table filterFilters only the rows rendered by a named collection node.Apply the same node policy to every occurrence of that nested table.

These two scopes follow the product decisions already made for the explorer; they are not defaults supplied by TanStack. Keep the filter model typed and translate it to TanStack column filters or a server query at one boundary.

Long values, hover previews, and details

The desired interaction is a good fit for a layered disclosure model:

NeedDefault UIAccessibility rule
Long content field in a cell Show a one-line or two-line ellipsis, plus a visible “View details” button when the full value matters. The complete value must remain available by click/tap and keyboard, not only by hover.
Quick supplementary preview Use a Base UI Popover anchored to a focusable trigger; it can open on hover with openOnHover and a delay, while still being usable from a keyboard-triggered interaction.[S21] Keep the preview supplementary and provide a non-hover path. For many cells, a controlled popover with a trigger payload/handle avoids mounting a separate complex popup for every value.[S21]
Important explanatory text Use inline text or a popover if space is limited. Do not hide essential meaning behind a tooltip; Base UI explicitly says tooltips are not reliable for touch users or assistive technologies.[S22]
Full item card with every field Open a right-side shadcn Sheet with field groups and a scrollable body. Keep a title, description, and visible close action. The Sheet extends Dialog, whose modal default traps focus, locks document scrolling, and disables pointer interaction outside the popup.[S23][S24]

Popover versus preview card: Base UI’s PreviewCard is deliberately a visual progressive enhancement for a link. Its preview content is not touch, keyboard, or screen-reader navigable, so it is suitable only when the destination contains the same information. For a table cell’s full value, use an accessible popover or sheet instead.[S25]

Overlay implementation caveats

Popover

  • Use the documented anatomy: Root, Trigger, Portal, Positioner, and Popup; add Title, Description, and Close when the popup needs them.[S21]
  • Prefer a real button or another explicitly accessible trigger. The trigger should expose what it opens; do not make a non-interactive text span the only hover anchor.
  • Use collision-aware positioning and a portal rather than hand-tuned global z-index values. shadcn’s own component guidance says overlay components handle their stacking; Base UI exposes positioner/collision APIs.[S9][S21]

Tooltip

  • Reserve it for supplementary visual labels. Do not use it as the only way to reveal the full value of a long content field.[S22]
  • Icon-only triggers still need a clear accessible name; Base UI’s examples use aria-label on the trigger, and the application remains responsible for meaningful labels.[S22][S17]

Sheet and Dialog

  • Compose a Sheet with SheetTrigger, SheetContent, SheetHeader, SheetTitle, SheetDescription, and optional footer/close parts. The right side is the recommended placement for item details on desktop, with responsive width and an internal scroll body.[S23]
  • Do not remove the close affordance just because Esc works. Base UI’s dialog API says that when a dialog is modal or focus-trapped, a Dialog.Close inside the popup is needed so touch screen-reader users can escape.[S24]
  • Dialog focus moves into the popup and returns to the trigger/previous element by default; use initialFocus and finalFocus only when the details workflow needs a deliberate destination.[S24]
  • For a panel with gestures or snap points, use a Drawer rather than stretching Dialog/Sheet beyond their documented purpose. Base UI explicitly distinguishes the two.[S24]

Suggested source boundaries

This is the smallest structure that keeps relationship semantics, table mechanics, and visual primitives from becoming one large component.

src/
├─ components/
│  ├─ ui/                     # shadcn source components (Base UI base)
│  ├─ explorer/
│  │  ├─ explorer-shell.tsx
│  │  ├─ item-details-sheet.tsx
│  │  ├─ truncated-value.tsx
│  │  └─ value-preview-popover.tsx
│  └─ tables/
│     ├─ collection-table.tsx # generic columns/filter/sort/expansion shell
│     ├─ articles-table.tsx
│     ├─ authors-table.tsx
│     └─ offices-table.tsx
├─ lib/
│  ├─ filters/                # typed view/table filter model
│  └─ relationships/          # path + related-item accessors
└─ data/
   └─ types.ts                # content fields, metadata, collection node types

Keep technical metadata and raw JSON out of the default column set, but include both in the details Sheet when the user explicitly opens an item. For content fields, use a truncation renderer that owns three states: short value, accessible full-value action, and optional supplementary preview.

Do not share one global TanStack table instance across nested collections. Share typed column/filter helpers where useful, but instantiate table state per collection node. This prevents an Authors filter from accidentally changing Articles pagination or Offices expansion.

Verification checklist before implementation is considered done

  • Scaffold: npm run build succeeds on the Node version required by Vite; aliases resolve in both the editor and Vite.
  • Runtime: npx shadcn@latest info --json confirms Base UI as the project base; generated overlay components use Base UI composition, not copied Radix asChild examples.
  • Tables: every expand control is keyboard reachable and labeled; nested filters do not mutate the root table; open branches behave intentionally after data refresh.
  • Long text: the full value is reachable by keyboard and touch without hover; popover content is supplementary; the details Sheet contains the authoritative complete value.
  • Overlays: opening a Sheet moves focus into it, Esc and the visible close action close it, and focus returns to the initiating details control. Popover positioning remains usable near viewport edges.
  • Dark-only: the first paint is dark, no light/system toggle is exposed, semantic tokens remain readable, and focus indicators are visible on the dark surfaces.
  • Responsive: wide tables scroll horizontally without hiding controls; the details Sheet has a usable width on narrow screens; hover is an enhancement rather than a required input modality.
