Phases 0–4

Establish a safe, testable core.

These phases create the repository and the contracts that every later feature depends on. They finish with a fake-backed Zesty client; no production UI is required yet.

  1. Accept the product contract
  2. Bootstrap the repository
  3. Define contracts and fixtures
  4. Secure browser inputs and view state
  5. Implement the Zesty API boundary
0

Accept the product contract

Depends on: noneType: human gate
  • Review the product specification, domain language, and both ADRs as one contract.
  • Resolve any contradiction before code or package choices make it expensive.
  • Receive explicit shared-understanding confirmation from the product owner.
  • Change the specification status from Proposed to Accepted and record the date.
  • Keep this implementation plan aligned if the accepted contract changes.

Output: accepted specification and a stable vocabulary.

Exit gate: no implementation work starts before the specification is explicitly Accepted.

Bootstrap the repository

Depends on: phase 0Milestone: M1
  • Create a pnpm-managed Vite React TypeScript application targeting Node.js 22.12+.
  • Install stable Effect v3, @effect/platform, TanStack Query, TanStack Table v9, and the selected test tools.
  • Initialize shadcn/ui with the Base UI base and Nova preset; add only components used by the first vertical slice.
  • Configure Tailwind semantic dark tokens and apply the permanent dark class before application code loads.
  • Bind the development server to 127.0.0.1:5173 with strict-port behavior.
  • Add formatting and lint rules that match the repository TypeScript preferences.
  • Configure @effect/language-service as the last TypeScript plugin and patch TypeScript from the package prepare script.
  • Add script placeholders for dev, check, test, test:e2e, test:performance, and build.
  • Create the initial module boundaries: domain, view-codec, collection-reference, zesty-api, explorer-core, and app.

Output: a dark-only application shell that builds and runs locally without external runtime assets.

Exit gate: pnpm check, pnpm test, and pnpm build run successfully from a clean install.

2

Define domain contracts and deterministic fixtures

Depends on: phase 1Milestone: M1
  • Model deployments, ZUIDs, collection references, content states, collection nodes, relationships, filters, sorting, and presentation state as explicit TypeScript types.
  • Separate raw API shapes, decoded API values, normalized snapshots, and persisted view state.
  • Define typed error variants for input, host, authentication, permission, missing resource, decoding, network/CORS, timeout, rate limit, server, and data limits.
  • Define stable IDs for collection snapshots, collection nodes, and content items.
  • Create small checked-in fixtures for Content and Blocks models, native relations, custom scalar relations, nulls, missing fields, duplicate matches, unmatched parents, long HTML, technical metadata, and malformed responses.
  • Create deterministic generators for 1,000, 10,000, and 50,000-item relationship graphs without real credentials.
  • Assert that fixture serialization and test diagnostics cannot contain token-shaped fields.

Output: reusable contracts and synthetic data shared by unit, browser, and performance tests.

Exit gate: representative fixtures decode into stable domain snapshots, while malformed fixtures produce the intended typed errors.

3

Secure browser inputs and shared view state

Depends on: phase 2Milestone: M1
  • Implement CollectionReferenceParser for allowlisted production, stage, and development Manager and Instances API URL shapes.
  • Validate instance, deployment, model ZUID, optional item ZUID, Content versus Blocks area, query strings, fragments, trailing slashes, and known editor suffixes.
  • Reject unknown hosts, invalid ZUIDs, new, import, and collection-area URLs without a model before any request is built.
  • Construct safe API and Manager targets exclusively from validated identifiers and the closed deployment mapping.
  • Implement a session-token store backed only by sessionStorage, with explicit set, read, and clear operations.
  • Implement ViewCodec with a versioned Effect Schema, canonical serialization, compression, fragment encoding, decoding, migration entry point, and encoded-length reporting.
  • Ensure the persisted view contains no token, pages, expanded rows, open panels, loading state, or other ephemeral values.
  • Preserve invalid raw view data long enough for a user to copy it or confirm reset; never silently replace it.
  • Add property-style round-trip tests and a corpus of malicious or malformed URL inputs.

Output: trusted collection references, isolated secret storage, and a deterministic non-secret URL codec.

Exit gate: fuzzed and table-driven parser tests prove that no untrusted hostname can become an authenticated request target.

4

Implement the Zesty API boundary

Depends on: phases 2–3Milestone: M1
  • Define the small ZestyApi interface for model schema and paged collection snapshot loading.
  • Implement the adapter with Effect, @effect/platform, and a fetch-backed client.
  • Send Authorization: Bearer <session token>, lang=en-US, and only documented query parameters.
  • Use no _active parameter for Latest saved and _active=true for Published.
  • Decode every response page once with Effect Schema, then normalize it into the domain snapshot.
  • Fetch subsequent pages until complete or the 10,000-item collection limit is reached.
  • Map status codes and transport failures into the typed error model without exposing request headers.
  • Apply bounded timeout and retry only for transient network failures, 429, and selected 5xx responses.
  • Expose cancellation and bounded concurrency primitives without coupling the API interface to React.
  • Test pagination, headers, content state, decoding, retry, timeout, cancellation, and limits through a fake transport or Effect Layer.

Output: a fully tested, fake-backed API adapter ready for TanStack Query.

Exit gate: API tests prove correct request construction and failure mapping without contacting Zesty or reading APP_SID.

Foundation completion check

  • The domain core imports no React, TanStack, Effect, browser storage, or network implementation.
  • The only code that sees the token is the token store and authenticated request adapter.
  • Every network target originates from the validated deployment mapping.
  • All tests are deterministic and offline.
