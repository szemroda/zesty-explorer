Local implementation roadmap

Build the smallest trustworthy Zesty Explorer.

This plan turns the product specification into fourteen implementation phases preceded by an acceptance gate. Each phase has explicit outputs and an exit gate; work should not advance while required behavior remains unverified.

Version 1 Node.js 22.12+ pnpm Local browser app No live Zesty in tests
Implementation prerequisite complete. The product specification was accepted on 2026-09-11. Implementation may proceed through the gated phases below.

Reading order

Phases 0–4

Foundation

Lock the contract, scaffold the repository, create fixtures, secure inputs, and build the API boundary.

Phases 5–10

Explorer

Deliver a root vertical slice, data orchestration, relationships, filtering, nested tables, and URL sharing.

Phases 11–14

Verification

Harden failure paths, automate browser checks, measure performance, and prepare the local handoff.

Required sequence

The order is dependency-driven. Small feedback loops are preferred, but a later phase must not force an unreviewed change to a contract established earlier.

0 Accept→1 Bootstrap→2 Contracts→ 3 Inputs→4 API→5 Root slice→ 6 Loading→7 Relationships→8 Querying→ 9 Nested UI→10 Sharing→11 Hardening→ 12 Browser checks→13 Performance→14 Handoff

Milestones and gates

Milestone Phases Observable result Gate

Rules that apply to every phase

Security

  • Never place a session token in a URL, log, fixture, snapshot, or error message.
  • Construct API hosts from an allowlisted deployment mapping; never trust a supplied host.
  • Use only GET requests to Zesty.
  • Render HTML content as inert text.

Performance

  • Normalize data once and reference content items by stable ID.
  • Join with indexes, not parent-by-child scans.
  • Mount only visible pages and expanded branches.
  • Add a Web Worker only after measurements justify it.

Testing

  • No automated test may contact a real Zesty instance or read a real cookie.
  • Test behavior at module seams instead of duplicating implementation details.
  • Use generated datasets for scale and checked-in fixtures for edge cases.

Scope control

  • Do not add hosting, a proxy, CI, analytics, editing, export, or mobile layout.
  • Keep Effect at asynchronous I/O boundaries and pure TypeScript in hot loops.
  • Record a new ADR only for a hard-to-reverse or surprising decision.

Release definition of done

  • Every acceptance statement in the product specification has a manual or automated verification path.
  • All six local commands documented in the specification exist and succeed for a clean checkout.
  • The application makes no non-Zesty runtime network request.
  • A shared URL restores the full non-secret view in another browser tab.
  • Representative 10,000- and 50,000-item datasets meet or clearly report the agreed performance budgets.
  • A teammate can follow the README without undocumented setup knowledge.
