Phases 11–14

Prove safety, usability, and performance.

The last phases exercise the complete application against offline fixtures, measure the agreed budgets, and leave a clean local workflow for the team. They do not introduce CI.

  1. Harden failures, limits, and security
  2. Automate browser and accessibility checks
  3. Measure and tune performance
  4. Complete documentation and handoff
11

Harden failures, limits, and security

Depends on: phases 5–10Milestone: M4 begins
  • Review every typed error and confirm it reaches a specific, actionable English UI message.
  • Verify a root failure blocks only the table area and offers retry.
  • Verify a descendant failure leaves the rest of the view usable and exposes retry at that node.
  • Keep incomplete-data warnings persistent anywhere a partial snapshot may affect filtering or results.
  • Do not present a descendant-dependent view filter as final while required snapshots are pending.
  • Confirm 401 clears only the session token and does not destroy URL state.
  • Confirm unknown hosts and cross-instance or cross-deployment nodes fail before authenticated networking.
  • Audit logs, errors, React Query dev state, test output, clipboard actions, and browser storage for token exposure.
  • Verify the application issues only GET and preflight requests and makes no analytics, CDN, font, or error-reporting calls.
  • Verify content HTML cannot execute in tables, popovers, details, errors, or copied formatted views.
  • Confirm all destructive view operations explain impact and require confirmation.

Output: explicit failure recovery and a documented security audit checklist with results.

Exit gate: every security invariant and failure state has a passing automated check or a recorded, repeatable manual check.

12

Automate browser and accessibility checks

Depends on: phase 11Milestone: M4
  • Run browser tests in Chromium against deterministic intercepted responses or an in-process fake transport.
  • Cover first use, token help, collection parsing, root loading, content-state switch, refresh, and 401 recovery.
  • Cover native and custom relationship creation, ambiguous relation selection, subtree removal, and enforced limits.
  • Cover global search, view filters, table filters, descendant predicates, sorting, facets, and pagination.
  • Cover nested expansion, repeated collection roles, details Sheet, raw JSON, copy value, popover, and Manager links.
  • Cover URL restoration, Copy view link, long-link warning, corrupt payload recovery, Reset view, and root replacement.
  • Cover partial collections, nested failures, stale field paths, empty collections, and request cancellation.
  • Verify keyboard access, focus order, focus restoration, visible focus, accessible names, table semantics, and dialog behavior.
  • Verify the compact layout at representative laptop and desktop viewport widths; mobile behavior is not a target.
  • Keep tests behavior-focused and remove redundant smoke assertions.

Output: a focused offline browser suite invoked by pnpm test:e2e.

Exit gate: the complete critical-path browser suite passes repeatedly without a real Zesty instance, session token, or external network dependency.

13

Measure and tune performance

Depends on: phases 7–12Milestone: M4 completes
  • Benchmark normalization, native and custom index construction, joins, nested predicates, free text, facets, sorting, and page selection with 1,000, 10,000, and 50,000 generated items.
  • Measure browser p50 and p95 for loaded-data filtering, sorting, row expansion, nested page changes, and debounced typing.
  • Observe long tasks, React commit duration, mounted row count, memory growth, and redundant recomputation.
  • Verify 10,000-item filtering or sorting completes within 250 ms and loaded row expansion within 100 ms.
  • Verify a 50,000-item view remains usable and expensive computations complete within one second.
  • Store local baselines with the dataset seed, Node/browser versions, machine context, and variance notes.
  • Make a result over twice the stored local baseline fail for investigation while still reporting absolute product targets.
  • First repair algorithms, cache identity, repeated decoding, unstable React props, excess DOM, and eager facets.
  • Introduce one module Web Worker only if representative runs still produce roughly 50 ms long tasks, blocked typing, or a p95 target miss after those repairs.
  • If a Worker is added, keep ExplorerCore contracts unchanged, transfer minimal serializable snapshots, cancel stale work, and repeat the same correctness suite on both execution paths.

Output: reproducible local performance reports and a measured main-thread-versus-Worker decision.

Exit gate: pnpm test:performance reports all agreed budgets; any miss has a documented cause and an accepted follow-up before release.

14

Complete documentation and local handoff

Depends on: phases 11–13Milestone: M5
  • Write an English README with prerequisites, clone/install/run commands, supported browsers, and the fixed localhost address.
  • Explain how to find the correct Zesty Manager cookie for production, stage, and development without ever pasting an example real token.
  • Explain collection URL sources, Content and Blocks support, Published behavior, relationship rules, limits, shared links, and reset behavior.
  • Document every local verification command and state that tests never use live Zesty or a real session token.
  • Document known limitations and first-version non-goals without presenting them as defects.
  • Update the product specification, domain language, ADRs, and this plan when implementation reveals an accepted contract change.
  • Run the full verification sequence from a clean install.
  • Ask a teammate unfamiliar with the implementation to clone, start, authenticate, open a collection, create one relation, filter it, and copy a view link using only the README.
  • Fix instructions or product affordances that required oral explanation.

Output: a reproducible local application and a self-sufficient team handoff.

Exit gate: a clean-clone rehearsal succeeds and the repository has no undocumented setup dependency.

Final command gate

pnpm install --frozen-lockfile
pnpm check
pnpm test
pnpm test:e2e
pnpm test:performance
pnpm build

There is deliberately no CI workflow. These commands form the repeatable local release check and must remain practical for contributors to run.

Final manual checks

  • Run the built application locally in current Chrome and Edge.
  • Use a permitted Zesty session only for a final human read-only sanity check, never for automated tests.
  • Inspect browser networking and confirm requests go only to the validated Zesty API host.
  • Copy a view URL and confirm it contains no token or ephemeral table state.
  • Clear the token and confirm the view remains recoverable.
